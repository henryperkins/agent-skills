# Release notes — 1.7.0

## 2026-08-17

Fixes the three high-severity findings from the Core AI skills source-of-truth audit. Each was verified against upstream source at the version the skills pin.

- Bumped plugin metadata to `1.7.0` in `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`.
- **`wp-abilities-api` — category registration example was unrunnable.** `references/php-registration.md` registered a category with `label` only. `WP_Ability_Category::prepare_properties()` throws `InvalidArgumentException` on a missing or non-string `description` exactly as it does for `label`, and `WP_Ability_Categories_Registry::register()` catches that into `_doing_it_wrong()` + `return null`. `WP_Abilities_Registry::register()` then rejects every ability naming the unregistered category, so the omission silently took out the category and all of its abilities — invisible without `WP_DEBUG`. Added `description` to the example and documented the requirement, cross-referencing the file's existing "How a bad registration fails" section. Verified against `wordpress-develop@7.1` and `@7.0` (identical).
- **`wp-abilities-api` — client-side examples raced package initialization.** `references/client-side.md` described `@wordpress/core-abilities` as auto-fetching server abilities with no async caveat, and the word `ready` appeared nowhere in the skill. `packages/core-abilities/src/index.ts` exports exactly one thing — `export const ready: Promise<void> = initialize()` — and its README instructs awaiting it before `getAbilities()` or `executeAbility()`. Added a "Registration is asynchronous" section, gated both imperative examples on `ready`, and noted that the skill's own enqueue pattern loads the package as a *sibling* script module, so the dynamic-import form is required rather than a static import. Verified against `gutenberg@v23.7.2`.
- **`wp-ai-client` — `using_abilities()` was described as agentic.** `SKILL.md` and `references/prompt-builder.md` claimed that when the model calls an ability, "execution routes back through the Abilities API's permission and execution machinery," making the client "agentic without writing function-calling boilerplate." `WP_AI_Client_Prompt_Builder::using_abilities()` builds `FunctionDeclaration` objects and terminates in `using_function_declarations()`; a `FunctionDeclaration` carries no callable, and no core path invokes the resolver. Code written from the old text shipped a silently non-functional feature. Replaced with the mandatory round trip — inspect `toMessage()`, run `WP_AI_Client_Ability_Function_Resolver::execute_abilities()`, feed the responses back via `with_history()` — and demoted the former "low-level" framing in step 7, which is now scoped to timeout policy. Verified against `wordpress-develop@7.1` and `php-ai-client@1.4.0`, including that the builder's `__call` proxy maps `with_history` to `withHistory`.

Remaining audit findings (18 medium, 15 low) are not addressed in this release.
