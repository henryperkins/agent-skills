# wp-abilities-api — PHP / REST / lifecycle audit against WP 7.1 (+ 6.9 / 7.0 / trunk)

Upstream paths below are relative to the 7.1 release package (`wp-includes/...`) unless prefixed with a branch/tag (`6.9:`, `7.0-tag:`, `trunk:`). Skill paths are relative to `skills/wp-abilities-api/`.

## Findings

- **[medium]** `SKILL.md:4` and `SKILL.md:234` — "Targets WordPress 6.9+ (PHP 7.2.24+)" / "This base skill supports PHP 7.2.24+ and WP 6.9+ ... on PHP 7.2 or 7.3, upgrade the site runtime or stop before installing the adapter" → PHP 7.2.24 is the floor for 6.9 only. WordPress 7.0 and 7.1 both ship `$required_php_version = '7.4'` (`wp-includes/version.php:40` in the 7.1 package; identical in the `WordPress/WordPress` `7.0` tag; the `6.9`/`6.9.3` tags say `'7.2.24'`). A 7.0/7.1 site cannot be on PHP 7.2/7.3, so the MCP-adapter PHP caveat applies to 6.9 sites only. → State the floor per version ("PHP 7.2.24+ on 6.9; 7.4+ on 7.0/7.1") and scope the PHP 7.2/7.3 warning to 6.9.
- **[medium]** `references/rest-api.md:419` — the 7.0-fallback snippet gates on `version_compare( get_bloginfo( 'version' ), '7.1', '>=' )` → `references/execution-lifecycle.md:43-47` says explicitly not to do this because pre-release builds (`7.1-RC4`) sort below `7.1`; confirmed with PHP: `version_compare('7.1-RC4','7.1','>=')` is `false`, `version_compare('7.1-RC4','7.1-alpha','>=')` is `true`. On an RC site the snippet takes the 6.9/7.0 branch and manually filters — harmless here, but it contradicts the skill's own rule. → Compare against `'7.1-alpha'` (or gate on `class_exists( 'WP_Filter_Sentinel' )`, absent in the 7.0 tag, present in 7.1 with `@since 7.1.0`, `wp-includes/class-wp-filter-sentinel.php:6`).
- **[low]** `references/execution-lifecycle.md:49-50` — "`execute()` also gained a `normalize_input()` failure check in 7.1 ... On 7.0 a normalization error fell through into validation." → On 6.9/7.0 core `normalize_input()` cannot return a `WP_Error` (no filter; `6.9:class-wp-ability.php:442-455`), so the described 7.0 failure mode only exists for a subclass override. 7.1 added the `is_wp_error()` check (`abilities-api/class-wp-ability.php:814-817`) because the new filter can now return one. → Reword to "7.1 checks `normalize_input()` for a `WP_Error` because the new `wp_ability_normalize_input` filter can return one; on 7.0 nothing in core produced such an error".
- **[low]** `references/rest-api.md:301-303` — "For raw registry data that bypasses filtering entirely, call `WP_Abilities_Registry::get_all_registered()`." → Upstream marks the class `@access private` (`abilities-api/class-wp-abilities-registry.php:18`) and the method "Do not use this method directly. Instead, use the `wp_get_abilities()` function." (`:220`). Behaviourally correct, but it recommends a non-public API without saying so. → Add "(private API — not covered by back-compat)" or drop the recommendation.
- **[nit]** `references/rest-api.md:66-69` — a form-encoded/multipart `POST` "either runs on schema defaults or fails `validate_input()` with a 400 complaining about a missing property" → with `null` input and no root `default`, `rest_validate_value_from_schema()` fails the *type* check first (`rest_is_object( null )` is `false`, `wp-includes/rest-api.php` `rest_is_object()`), so the 400 reads "input is not of type object.", not a missing-property message. → Say "complaining that `input` is not an object".
- **[nit]** `references/php-registration.md:168` — `category` "**Required**" → correct through 7.1 (`abilities-api/class-wp-ability.php:295-299` throws on empty category), but trunk (7.2-alpha) makes it optional with default `uncategorized` (`trunk:class-wp-abilities-registry.php:147-149`, `@since 7.2.0` at `:44`). No discrepancy for the 7.1 target; flagging because the skill otherwise tracks trunk. → Optional forward note once 7.2 ships.
