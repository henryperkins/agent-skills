## Findings

- **[high]** `references/client-side.md:54-76` (also `:36-45`, `SKILL.md:228`) — "`my-plugin-admin` declares `@wordpress/abilities` as its dependency, not `@wordpress/core-abilities` — the two are enqueued as siblings" + `const { ready } = await import( '@wordpress/core-abilities' )` → the dynamic import cannot resolve. WP 7.1 `wp-includes/class-wp-script-modules.php:709-716` builds the import map from *dependencies* of enqueued modules only ("the script modules in $this->queue are not included in the importmap because they get printed as scripts"), and `get_dependencies()` (`:759-790`) never returns its roots. Ran the 7.1 class with the skill's exact registration: import map = `["@wordpress/abilities"]`; `@wordpress/core-abilities` is printed as a `<script type="module">` but is not a resolvable bare specifier, so `import('@wordpress/core-abilities')` throws `TypeError: Failed to resolve module specifier`. → Declare it as a dependency of the plugin module — `array( 'id' => '@wordpress/core-abilities', 'import' => 'dynamic' )` for the `await import()` form (exactly what core's own `workflow/index.js` does, `wp-includes/assets/script-modules-packages.php:378-386`), or the plain string for a static import — and drop the separate `wp_enqueue_script_module( '@wordpress/core-abilities' )`; harness with the dynamic dep yields `["@wordpress/abilities","@wordpress/core-abilities"]`.
- **[high]** `references/mcp-exposure.md:28` "designed to be a Composer dependency, not a standalone plugin install for distributed use", `:49` "standalone plugin zip … fine [for smoke tests]. Don't ship that to production", `SKILL.md:234` composer + jetpack-autoloader + `McpAdapter::instance()` as the install path → inverted relative to upstream at the pinned tag: `README.md:57-59` "### As a WordPress Plugin (Recommended) — MCP Adapter is designed to be installed as a WordPress plugin"; `docs/getting-started/installation.md:7` "Method 1: WordPress Plugin (Recommended)"; Composer is a secondary path "for plugin developers" (`README.md:79-81`). 0.6.0 bundled Jetpack Autoloader into the plugin precisely so the standalone plugin and bundled copies coexist newest-wins (trunk `CHANGELOG.md` 0.6.0 "Changed"). Trunk goes further (see §3: #289 removes the Composer docs, #288 deprecates bundled use with `_deprecated_function()`). → Recommend installing/activating the plugin (`wp plugin install https://github.com/WordPress/mcp-adapter/releases/latest/download/mcp-adapter.zip --activate`), depending on it via `Requires Plugins: mcp-adapter` + `class_exists( 'WP\MCP\Core\McpAdapter' )`, and describe Composer bundling as legacy/deprecated-on-trunk; also note `automattic/jetpack-autoloader` is already a hard `require` of `wordpress/mcp-adapter` (`composer.json` require), so the second `composer require` is redundant and the real prerequisite is `config.allow-plugins`.
- **[medium]** `references/client-side.md:42-45` — "siblings have no guaranteed evaluation order, so a static import may not have a resolved binding when your code runs" → wrong mechanism. ES modules evaluate a static import's target before the importer, so once `@wordpress/core-abilities` is declared as a static dependency `ready` is always bound (harness: import map contains it and WP emits `<link rel="modulepreload">`, `class-wp-script-modules.php:585-618`); if it is *not* declared, a static import fails to link at all rather than yielding an unresolved binding. The only real trade-off is static = REST fetches start at page load, dynamic = deferred (which the skill already states). → Replace the sibling-ordering sentence with the dependency-declaration rule.
- **[medium]** `references/client-side.md:50-89`, `SKILL.md:228` — enqueue snippets load no classic globals. WP 7.1's built `wp-includes/js/dist/script-modules/abilities/index.js:32-42` does `module.exports = window.wp.data` / `window.wp.i18n` and dereferences them at module evaluation (`:7264-7271`); `core-abilities/index.js:27-38` reads `window.wp.apiFetch` / `window.wp.url`. `wp_default_script_modules()` (`wp-includes/script-modules.php:170-236`) ignores the `dependencies` key of `script-modules-packages.php`, and `WP_Script_Modules::register()` args accept only `in_footer`/`fetchpriority` (`class-wp-script-modules.php:129-133`), so nothing enqueues them for you; a plain admin screen gets only `common`→`wp-a11y`→`wp-i18n` (`script-loader.php:766`, `script-loader-packages.php:2-6`), not `wp-data`, `wp-api-fetch`, `wp-url`. → Add `wp_enqueue_script( 'wp-data' )` (plus `wp-api-fetch`, `wp-url` when `@wordpress/core-abilities` is used) to the page-scoped enqueue, or make the plugin's classic script depend on them.
- **[low]** `references/client-side.md:25-28` — "if the categories request fails, every `registerAbility()` throws …, the first throw aborts the rest of the loop, and you get a partially populated store" → with no categories the *first* `registerAbility()` throws (`packages/abilities/src/store/actions.ts:90-103`) and the loop in `packages/core-abilities/src/index.ts:112-125` aborts before registering anything: zero server abilities, not a partial set.
